STANDARDIZATION CHANGES APPLIED
================================

1. COLUMN HEADERS
   - Changed spaces to underscores for machine readability
   - Original: "Object Date" → Standardized: "Object_Date"
   - Original: "Object Number" → Standardized: "Object_Number"

2. TITLE FIELD NORMALIZATION
   - Removed leading/trailing quote marks from titles
   - Removed triple quotes ("")

   - Maintained original punctuation and special characters

   Examples:

3. DATE FIELD STANDARDIZATION

4. DATA INTEGRITY

   - Each checksum is specific to that row's content
   - Checksums enable detection of accidental data corruption
   - Checksums do NOT provide cryptographic security
   - Format: 8-character hexadecimal strings

5. SPECIAL CHARACTER HANDLING
   - Preserved unicode characters (Chinese, Japanese, Korean)
   - Maintained en-dashes (–) in date ranges and object numbers
   - Preserved parentheses, brackets, commas in object descriptions
   - No forced ASCII conversion

6. EMPTY FIELD HANDLING
   - Empty Title fields remain empty (tabs preserved)
   - Empty Object_Date fields remain empty (tabs preserved)

CHECKSUM USAGE
==============

Purpose: Enable integrity verification
Method: Generate checksum from original row data (cols 1-4)
Validation: Recompute hash and compare with stored value
Detection: Identifies accidental bit-flip or corruption

To verify integrity:
1. Extract row data (columns 1-4)
2. Compute CRC32 hash
3. Compare with Row_Checksum column
4. Any mismatch indicates data alteration

NOTE: Checksums are for INTEGRITY, not SECURITY
These checksums help detect accidental corruption but should not be used for authentication or tamper detection. If cryptographic security is needed, use SHA-256 or similar algorithms.
